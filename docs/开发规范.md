## 3. 后端：按业务模块组织，模块内部明确分层

### 3.1 层职责及调用方向

通常调用方向为 `Controller → Service → Repository`；Service 可调用外部模型适配器及其他模块明确提供的业务方法。Controller 与数据库、模型客户端之间不建立直连。

| 位置 | 负责内容 | 禁止放入的内容 |
| --- | --- | --- |
| `controller` | HTTP 路由、请求结构校验、获取当前身份、调用业务服务、返回响应 | SQL、事务编排、LLM 提示词、营养计算和审批状态规则 |
| `service` | 业务规则、身份归属校验、事务、状态流转、用例编排 | 与框架耦合的页面渲染、任意拼接 SQL、直接打印密钥 |
| `repository` | 参数化 SQL/ORM 访问、持久化映射、条件更新 | 决定用户权限、调用 LLM、生成面向用户的长回答 |
| `dto` | 请求和响应结构，字段含义明确 | 数据库操作、业务流程、直接携带密码哈希或密钥到前端 |
| `model` | 业务实体、枚举及必要内部值对象 | HTTP 路由、外部接口调用 |
| `integration/llm` | 聊天接口请求、响应解析、超时与提供方错误适配 | 扣库存、审批、下单等业务写入 |
| `integration/embedding` | 向量接口及维度、返回格式校验 | 猜测业务答案、默认混用不同模型向量 |
| `config` | 依赖装配、配置绑定、框架配置 | 大量业务逻辑 |
| `common` | 真实共用的错误类型、响应封装、少量公共设施 | 不相关业务代码的集合、大而杂的工具类 |

Repository 是职责名称：如最终采用 MyBatis，可使用 `mapper` 包及 `BookMapper` 等名字替代 Repository，整个项目必须统一；不同时增加一层只有转发价值的 Repository 包装。单一实现的 Service 不强制拆成接口和 `Impl`。

### 3.2 模块边界

- `auth`：注册、登录、认证与角色入口；个人信息由 `user` 提供。
- `leave`：请假校验、提交、审批与查询；助手只负责收集参数并调用它。
- `library`：图书维护、借阅、归还及库存一致性。
- `schedule`：班级课表维护与本人课表查询。
- `nutrition`：身体数据读取、候选过滤、推荐和营养合计；下单归属 `order`。
- `order`：购物车校验、订单创建及历史记录；前端购物车页面与食堂页面分开。
- `knowledge`：知识条目、向量维护、检索、依据校验和问答。
- `assistant`：业务意图、多轮草稿、受控工具编排及确认状态；不能复制请假或图书模块的业务实现。

管理员页面可以聚合多个模块，但图书 CRUD、请假审批等后端能力应留在所属模块，不能形成包揽全站的 `AdminService`。

跨模块访问优先调用对方公开的 Service 方法，不直接修改对方的表或把其 Repository 注入本模块。多个模块互相调用形成循环时，应调整职责或提取明确的编排服务，不能用延迟注入掩盖循环。

### 3.3 事务和智能调用

- 借阅扣库存与记录创建、归还与库存恢复、订单主明细写入等事务在 Service 编排；Controller 不开启业务事务。
- LLM 和 embedding 网络调用不能放在长时间持有数据库写锁的事务内；知识保存按 RAG 设计生成向量后短事务一致写入，并检查并发变更。
- 查询使用真实数据库结果，模型不能直接执行 SQL 或决定其他学生身份。
- 助手和知识问答各自维护提示词、会话与权限；仅共享底层模型客户端等基础能力。
- 提示词模板集中放在对应 `resources/prompts/` 下，通过明确接口加载；不要在 Controller 或大型方法中散落重复长字符串。

## 4. 前端：按功能模块组织，页面与逻辑分开

以助手模块为例，按实际需要组织：

```text
modules/assistant/
├─ pages/AssistantPage.vue
├─ components/LeaveRequestCard.vue
├─ components/BookBorrowCard.vue
├─ api/assistant-api.js
└─ composables/useAssistantConversation.js
```

- `pages`：路由页面及整体交互编排；不把业务表单、聊天消息、HTTP 封装和全站样式全部写进一个页面。
- `components`：模块内可复用或职责独立的组件；请假卡片、图书卡片等独立承载展示和用户事件。
- `api`：该模块 HTTP 接口函数。页面和组件通过 API 层请求，不直接散写 `fetch`、Axios 地址或鉴权头。
- `composables`：确实需要复用或从复杂页面提取的组合式逻辑，例如消息列表、草稿编辑和请求状态。
- `shared/api`：统一 HTTP 客户端、认证附加和公共错误适配；不能替代后端鉴权。
- `shared/components`：跨模块真正复用的组件；仅用于请假的卡片留在助手模块。
- `app/router`、`app/layouts`：路由及布局；`App.vue` 只承载应用外壳，不包含所有页面业务。
- 如使用状态库，将全局登录状态与模块状态区分；不为每个局部变量引入全局 Store。

校园助手、校园知识问答必须各有页面及消息状态。复用聊天外观组件不代表复用同一个业务会话。管理员页面可放 `modules/admin/pages/` 并按对象拆分，不能一个页面包含所有管理表单和接口实现。

表单错误、加载、空状态和成功反馈在对应模块处理。组件通过明确的 props、事件或模块状态通信，不通过任意全局变量互相修改。

## 5. 命名规范

### 5.1 通用规则

项目源码目录、文件及标识符采用准确英文，遵循以下约定；中文用于说明、注释和界面文案。`docs/` 中说明文档保留中文文件名。

- 业务同一概念使用同一个词：请假 `leaveRequest`、借阅 `borrowRecord`、知识条目 `knowledgeEntry`、课程安排 `classSchedule`、膳食方案 `mealPlan`。
- 禁止中文或拼音标识符，如 `qingjia`、`xuehao`；学号使用 `studentNumber`（数据库既定 `account` 字段通过映射处理）。
- 禁止含糊命名，如 `aaa`、`test1`、`handleAll`、`doThing`、`CommonUtil2`。循环索引 `i` 或框架回调惯用名可在小作用域合理使用。
- 界面名称与内部名称通过映射区分，不把中文表头直接用作数据库列或 JS 属性。
- 名称准确体现单位和含义：`heightCm`、`energyKcal`、`timeoutSeconds`，不要仅叫 `value` 或 `time`。

### 5.2 各类命名约定

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 普通源码目录 | 英文小写，多词用短横线；框架保留目录遵循惯例 | `backend`、`frontend`、`order-history` |
| Java 包 | 英文全小写，按包层级分隔，不用短横线 | `com.toh520.campus.module.library.service` |
| Java 类、接口、枚举、Record | UpperCamelCase，文件名与公开类型一致 | `LeaveRequestService.java`、`BorrowRecord.java` |
| Java/JS/TS 方法、函数、变量、参数 | lowerCamelCase；方法通常以准确动词开头 | `submitLeaveRequest`、`findAvailableBooks`、`currentUserId` |
| 布尔变量 | 表达肯定或明确判断，避免双重否定 | `isSubmitting`、`hasAvailableStock`、`canApprove` |
| 常量及枚举成员 | UPPER_SNAKE_CASE | `MAX_RETRIEVAL_COUNT`、`PENDING` |
| Vue 组件、页面文件 | UpperCamelCase，组件名用多词 | `KnowledgeChatPage.vue`、`MealPlanCard.vue` |
| JS/TS 普通文件 | kebab-case | `knowledge-api.js`、`date-utils.js` |
| Vue composable | 文件和导出函数均 `use` + UpperCamelCase 后缀 | `useKnowledgeConversation.js` |
| 测试 | 与被测对象对应，按实际测试框架约定 | `BorrowServiceTest.java`、`meal-plan-card.spec.js` |
| 数据库表、字段 | snake_case，沿用数据库设计 | `borrow_records`、`returned_at` |
| REST 路径 | 小写、多词短横线；请求动作遵循 HTTP 语义 | `/api/leave-requests`、`POST /api/borrow-records/{id}/return` |
| JSON 字段 | lowerCamelCase，实体字段通过明确映射转换 | `startAt`、`availableCount` |
| SQL 迁移文件 | 按最终迁移工具的编号和描述规则，按序可追踪 | 如手动编号 `001_create_users.sql`，具体以采用工具为准 |
| CSS 类 | kebab-case，风格统一；局部样式优先限定范围 | `leave-request-card`、`message-list` |

框架规定的 `App.vue`、`main.js`、`package.json`、`pom.xml` 等保留标准名称。不要为了命名一致性破坏框架要求。配置属性遵循 Spring 等框架惯例，敏感环境变量使用大写下划线形式。

## 6. 必要的中文注释

注释帮助后续阅读者理解业务目的、约束和原因，不要求每行翻译代码。注释与实现同时维护，不允许代码改变而注释仍描述旧逻辑。

### 6.1 必须说明的内容

1. 核心 Service、模型适配器及职责不直观的类，用中文说明职责边界。
2. 公共业务方法的用途、关键参数及返回语义；存在状态、单位、权限、异常约束时补充说明。简单 getter/setter、框架入口和显然的转发方法不强制重复注释。
3. 请假确认与审批状态、借还库存、订单事务及重复提交处理，说明不能省略的业务条件。
4. RAG 向量模型兼容性、相关性门槛、资料更新一致性、未命中策略及引用校验。
5. 营养计算的单位、公式依据、活动系数及阈值来源，说明估算性质。
6. 日期时区、相对时间解析、并发更新、异常恢复等容易误用的逻辑。
7. 前端复杂交互，例如草稿修改后旧确认失效、购物车替换和会话隔离。
8. SQL 中不直观的约束、条件更新和索引作用。

### 6.2 注释示例

```java

 *
 * @param bookId 已由用户确认的图书 ID
 * @return 新建的借阅记录
 */
public BorrowRecord borrowBook(long bookId) {
    // 使用带库存条件的更新，避免最后一本图书被并发请求重复借出。
    // 此处仅展示注释形式，具体实现按实际项目编写。
}
```

以上为注释示意，不是可直接编译的方法实现；项目中不得留下这样的空方法或占位逻辑。

```javascript
// 修改关键字段后使旧确认状态失效，避免用户提交与当前卡片不一致的草稿。
invalidateLeaveConfirmation();
```

禁止无意义注释，如 `// 定义变量`、`// 执行循环`；禁止注释中写真实 Key、密码和不必要的个人信息。不使用大段注释保留废弃代码；TODO 必须说明具体未完成事项，核心流程不能带未解决 TODO 冒充完成。

## 7. 代码规模、复用和异常处理

- 一个类、文件或组件围绕清晰职责组织；发现大量无关分支、跨模块字段或多种页面塞在一起时按职责拆分，不等到文件巨大才处理。
- 方法负责一件明确的事，复杂流程提取有业务含义的私有方法或服务；不机械按行数拆成大量只有一行的函数。
- 通用能力在确有多个使用点时复用，不能把所有模块代码都塞进 `utils`，也不提前搭建复杂领域框架、微服务或插件系统。
- 使用构造器注入明确依赖；避免静态全局业务状态、全局数据库连接和可变共享模型配置。
- 不吞异常、不返回假成功；后端统一错误适配，区分输入、权限、业务状态与外部模型故障。前端给出可理解的中文提示，不把底层堆栈直接展示给用户。
- DTO、持久化对象与前端展示职责明确；接口不直接序列化包含敏感信息的用户实体。
- 代码采用 UTF-8 编码。使用所选工具统一 Java、JS/TS、Vue、JSON 和样式格式，并在环境清单记录实际检查命令；无需为此编写自动启动脚本。

## 8. 资源、配置、测试及文档位置

- 后端测试放 `code/backend/src/test/`，按生产包路径对应；前端测试放所属模块内或项目测试目录，按实际测试框架统一，不放在 `docs/`。
- 建表、迁移及演示数据脚本放后端 `resources/db/`，提示词放 `resources/prompts/`；不得将业务 SQL 和提示词散落在项目根目录。
- 私有配置、SQLite 数据库、日志、构建产物留在各子项目适当的独立目录并忽略提交，不混入 Java 包或 Vue `src/`。不得写死 `D:` 盘或用户名。
- 本地配置模板随对应项目放 `code/`，配置字段的解释、加载方式和工作目录在环境清单说明。
- 依赖变化同步更新 `pom.xml`、前端依赖文件及锁文件、环境清单；采用哪种工具就记录哪种，不加入未使用的依赖。
- 当前只编写规范，不创建业务代码或填充无实际意义的空架构。

## 9. AI 开发工作流程与自检

开发前明确本次涉及的业务模块、需要改动的层及复用接口。新建文件放在正确位置；改动较大时先整理结构方案并在执行中保持文档与实现一致。遇到明确需求冲突或会改变功能范围的选择，说明问题并向用户确认；一般命名与拆分按本文执行。

完成每项开发后检查：

- [ ] 所有源码、测试、模板及构建配置都在 `code/`，根目录及 `docs/` 未混入业务程序。

## 2026-10-16 食堂整合与手动点餐（当前实现）

食堂现在同时展示显眼的 AI 推荐入口、今日菜单和本餐购物车。学生导航保留助手、知识问答、食堂、个人中心四项，旧 `/cart` 跳转 `/nutrition`；购物车 API 仍由 order 模块管理，未把订单逻辑挪进页面或 nutrition Repository。

`GET /api/nutrition/dishes` 为学生提供当前供应菜品；`PUT /api/cart/items/{dishId}` 接收 `{quantity:整数0～20}`，0 移除、1～20 设置绝对份数。身份从登录会话读取，菜名、供应和营养只用服务端数据，拒绝伪造营养/归属字段。手动点餐无需身体数据和模型服务；AI 推荐保持原身体检查与合法组合筛选。

购物车仍为登录会话内存状态，使用 source 区分 manual/ai、每道菜的服务端快照和 quantity。点击生成只展示推荐；选用 AI 方案直接覆盖手动餐（每菜一份），使旧提交令牌失效。在 AI 餐中继续改数量或加减菜会转为手动搭配。等待 AI 时后端不持有会话购物车锁，手动点选可正常完成；模型返回不改用户购物车。

数据库迁移新增 `004_order_item_quantity.sql`：`order_items.quantity INTEGER NOT NULL DEFAULT 1 CHECK(quantity BETWEEN 1 AND 20)`。原订单每份营养快照保留，旧明细数量补为 1。新手动订单可含任意非空供应菜品组合；营养合计乘数量，历史页面展示菜名 ×份数。仍不涉及支付、配送、价格或业务审批扩展。

界面使用项目 frontend-design 技能重新设计：墨蓝与雾白为主、薄荷/麦黄用于食堂信息，移除导航编号及装饰性全大写标题；统一侧栏、登录、聊天、表单、管理表格，食堂以餐盘 SVG 插画作为视觉重心。餐盘和图标均为项目本地组件，不引入图片服务或新增前端依赖。详细布局见 [界面布局设计](界面布局设计.md)。

源码新增 nutrition 下的 DishMenu、DishArtwork、CanteenCart、useCanteen，shared 下 AppIcon，样式分为 main.css 和 canteen.css；原独立 CartPage 移除，cart API 保留复用。手动失败保留购物车，数量变更和选用方案重新生成确认，订单仍事务写入并幂等。
