# 智慧校园最小数据库设计

版本：v0.4（补充知识向量字段，数据库为建议）  
更新日期：2026-10-15

## 1. 设计原则

- 仅围绕已提出的功能建表，不预设支付、通知、审计、会话、工作流等模块。
- 后端 Java、前端 Vue 已确认；本设计为逻辑模型。为便于换电脑运行，建议用 SQLite 和 Java JDBC 驱动，字段类型及 SQL 按最终数据库调整。
- `id` 为内部主键；账号唯一；身份由登录会话确定，不信任前端传入的归属 ID。
- 所有时间采用明确统一的上海时区语义，接口输出 ISO 8601（例如 `2026-10-09T09:00:00+08:00`）。SQLite 可采用带时区的 ISO 文本保存；不混存 UTC 与无时区本地文本。
- 周课表只存本地星期和时间。记录只添加业务需要的时间，不给每张表统一附加无用途的创建/更新时间。
- 下文共 10 张表，包含已确认的还书字段。购物车按最简临时状态设计，不新增购物车、套餐或推荐历史表。

## 2. 关系概览

```text
classes 1 -- N users
classes 1 -- N class_schedules
users   1 -- N leave_requests
users   1 -- N borrow_records N -- 1 books
users   1 -- N orders 1 -- N order_items N -- 1 dishes
knowledge_entries（独立知识条目）
```

SQLite 必须为每条数据库连接启用外键约束。涉及业务记录的关联采用限制删除，不使用级联删除历史记录。

## 3. 字段定义

字段均按最小功能定义；除明确可空字段外均不可空。所有主键为整数自增。

### 3.1 `classes` 班级

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键 |
| name | TEXT | 班级名称，唯一 |

首版预置一条班级记录，保留表是为了准确表达“学生属于班级，班级拥有课表”，无需新增班级管理功能。

### 3.2 `users` 用户

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键 |
| account | TEXT | 登录账号，唯一；学生固定为注册学号，管理员为预置账号；保留学号前导零 |
| password_hash | TEXT | 安全密码哈希，不保存明文 |
| name | TEXT | 姓名 |
| role | TEXT | `student` / `admin` |
| class_id | INTEGER，可空 | 关联 classes；建议学生注册时自动分配唯一演示班级，管理员可空 |
| age | INTEGER，可空 | 年龄；推荐时校验 18～80 |
| sex | TEXT，可空 | `male` / `female`，用于能量估算 |
| height_cm | REAL，可空 | 身高；推荐时校验 100～250 |
| weight_kg | REAL，可空 | 体重；推荐时校验 25～250 |
| activity_level | TEXT，可空 | `low` / `medium` / `high` |
| diet_preference | TEXT | `none` / `vegetarian`，默认 `none` |
| avoided_ingredients | JSON / TEXT | 需避开食材的字符串数组，默认 `[]` |

注册只接收姓名、学号、密码，学号存入 `account`，不增加重复学号字段。后端固定 `role = student`，保存密码哈希并按建议分配班级；管理员账号由初始化创建，不通过注册接口创建。数据库唯一约束处理并发重复注册。

身体信息直接放用户表，在个人中心维护，避免只有一对一数据却额外拆表。新注册学生的身体字段允许为空；点击 AI 推荐时先检查完整性，缺失则提示补全，不调用模型。JSON 用标准解析器序列化，不使用逗号切割；首版不按列表元素执行数据库统计。

### 3.3 `class_schedules` 班级课表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键 |
| class_id | INTEGER | 关联 classes |
| course_name | TEXT | 课程名称 |
| teacher | TEXT | 教师姓名 |
| weekday | INTEGER | 1～7，对应周一至周日 |
| start_time | TEXT | `HH:mm`，上海本地时间 |
| end_time | TEXT | `HH:mm` |
| classroom | TEXT | 教室 |

一行代表一段课程。校验 `start_time < end_time`，同班级同星期课程不能时间重叠；无需单独课程表、教师表、教室表或学生课表副本。

### 3.4 `leave_requests` 请假申请

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键 |
| user_id | INTEGER | 申请人，关联 users |
| start_at | TEXT / DATETIME | 请假开始时间 |
| end_at | TEXT / DATETIME | 请假结束时间 |
| reason | TEXT | 理由 |
| status | TEXT | `pending` / `approved` / `rejected`，默认 `pending` |

姓名从用户关联读取，不重复保存；只保存提交后的申请，不保存对话草稿。申请提交时间、审批人、审批意见与审批时间不在原始最小需求中，首版不增加。

状态流转：

```text
pending -> approved
pending -> rejected
approved / rejected -> 终态，不再次变更
```

审批采用条件更新 `WHERE id = ? AND status = 'pending'`，检查实际更新行数，防止重复或并发审批覆盖结果。

### 3.5 `books` 图书

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键 |
| title | TEXT | 书名 |
| author | TEXT | 作者 |
| summary | TEXT | 内容简介 |
| available_count | INTEGER | 当前可借数量，非负 |

不强制书名唯一，同名不同作者可以存在。借阅确认使用 ID 区分。首版只保存可借数量，不另存总量和在借数量；在借记录可查询计算。管理员修改库存代表盘点后的可借数量，不自动推断采购或丢失。

### 3.6 `borrow_records` 借阅记录

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键 |
| user_id | INTEGER | 借阅人，关联 users |
| book_id | INTEGER | 图书，关联 books |
| borrowed_at | TEXT / DATETIME | 借阅时间 |
| returned_at | TEXT / DATETIME，可空 | 归还时间，未归还时为空 |

`returned_at IS NULL` 表示在借，否则为已归还，不额外保存重复状态字段。建议约束同一用户和图书只能有一条未归还记录；SQLite 可用部分唯一索引实现；MySQL 等数据库采用适合其事务及锁机制的重复借阅控制，不照搬不支持的部分索引语法。归还后允许再次借阅。

借阅事务先执行带库存条件的扣减，成功后插入记录；失败回滚。归还事务先把本人尚未归还的记录置为已归还，成功后恢复库存；任何一步失败都回滚。借还均直接完成，不设审批表。已被借阅的图书禁止删除，历史借阅记录不直接删除。

### 3.7 `dishes` 菜品

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键 |
| name | TEXT | 名称 |
| category | TEXT | `staple` / `protein` / `vegetable` |
| portion_g | REAL | 每份重量（g），正数 |
| energy_kcal | REAL | 每份能量（kcal），正数 |
| protein_g | REAL | 每份蛋白质（g），非负 |
| fat_g | REAL | 每份脂肪（g），非负 |
| carbohydrate_g | REAL | 每份碳水（g），非负 |
| ingredient_tags | JSON / TEXT | 食材及过敏原标签数组，默认 `[]` |
| is_vegetarian | BOOLEAN / INTEGER | 是否素食，限定 0 / 1 |
| is_available | BOOLEAN / INTEGER | 是否供应，默认 1，限定 0 / 1 |

营养值按每份统一口径；管理员校验营养克数与份重明显不合理的输入，能量和三大营养素换算允许估算误差。标签使用统一名称，避免同一食材多种写法导致过滤失败。无标签不能被解释为保证无过敏原。

### 3.8 `orders` 订单

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键，同时作为课设订单 ID |
| user_id | INTEGER | 下单人，关联 users |
| ordered_at | TEXT / DATETIME | 下单时间 |

没有支付和履约流程，因此不增加金额、支付状态、地址、订单状态字段。

### 3.9 `order_items` 订单菜品明细

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键 |
| order_id | INTEGER | 关联 orders |
| dish_id | INTEGER | 关联 dishes |
| dish_name | TEXT | 下单时的菜名快照 |
| portion_g | REAL | 下单时每份重量快照 |
| energy_kcal | REAL | 下单时每份能量快照 |
| protein_g | REAL | 下单时蛋白质快照 |
| fat_g | REAL | 下单时脂肪快照 |
| carbohydrate_g | REAL | 下单时碳水快照 |

按建议的单套餐购物车设计，每道菜固定一份，不设数量字段；每张订单三条明细。`(order_id, dish_id)` 唯一。只有购物车确认提交才写入订单及明细，加入、替换或移除购物车套餐不会写入订单表。快照是为了管理员修改菜品后历史订单仍保持下单时内容，不属于无效重复。方案营养合计在查询时求和，不在订单主表重复保存。

不建立套餐表：套餐只是本次推荐产生的三个菜品 ID 组合。如果后续要求一张订单购买多个套餐或编辑份数，再增加明细数量及必要的套餐分组，当前不提前增加字段。

### 3.10 `knowledge_entries` 知识条目

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER | 主键 |
| title | TEXT | 条目标题，用于展示引用来源 |
| category | TEXT | `rule` / `course` / `activity` / `other` |
| content | TEXT | 完整知识正文 |
| embedding | TEXT | 标题及正文对应的数值向量 JSON 数组，必须与原文一起保存 |
| embedding_model | TEXT | 生成向量所用服务及模型的稳定标识；不同模型不能混算相似度 |

正文不能为空，活动日期直接写入正文。每条短文首版建议作为一个向量检索单元，不新增分块表。维度通过数组长度计算，后端校验模型要求的维度、数值有效且范数非零，不重复保存维度字段；同一模型标识对应固定维度和处理方式。

新增或编辑先生成新向量，再在短数据库事务中一致写入标题、正文、向量和模型标识，调用外部模型期间不持有数据库写锁。失败不保存半成品，编辑失败保留旧版本；并发编辑需检测原版本是否被其他请求修改。删除记录即删除其向量。首版直接读取数据库计算相似度，不维护需要另行同步的持久化索引。

切换 embedding 模型或维度时需要对全库重新向量化，只查询与当前问题向量兼容的数据；重建未完成时明确提示知识库未就绪，不把配置不兼容误报为无答案。详见 [RAG知识问答设计](RAG知识问答设计.md)。

## 4. 约束和索引

必须设置：

- 账号、班级名称唯一。
- 所有外键和规定枚举；库存非负、营养值合法、星期范围有效。
- `users(class_id)`、`class_schedules(class_id, weekday, start_time)`。
- `leave_requests(user_id)`、`leave_requests(status)`。
- `borrow_records(user_id, borrowed_at)`，以及同一用户同一图书最多一条在借记录的约束或等价事务控制。
- `orders(user_id, ordered_at)`、`order_items(order_id)` 和明细组合唯一约束。
- 所有外键列具备支持关联查询与删除检查的索引，已有复合索引覆盖前缀时不再重复建立。

向量按 JSON 保存时，普通 B-tree 不能加速余弦相似度检索；首版按课设小规模数据由 Java 扫描计算，不添加无效的向量列普通索引。

## 5. 不落库的临时数据

- 助手当前会话、待确认请假/借阅草稿、膳食候选和推荐方案。
- 单套餐购物车：建议按用户及当前登录会话保存服务端临时状态，包含套餐的三个菜品 ID、展示摘要和用于检查变更的身体/菜品数据指纹。刷新页面从服务端恢复，退出登录或服务重启清空，不新增持久化购物车表。
- 绑定用户的短期确认令牌及其处理结果，可由服务端短期状态管理；首版单进程内存方案允许重启后失效，不能重启后仍接受旧令牌。
- 身体能量计算结果、营养总量、库存派生统计。

加入购物车验证套餐确实来自本用户的有效推荐。购物车变更后旧提交令牌失效；提交时读取服务端购物车，复查供应状态、身体及菜品变更，再在事务中创建订单。推荐及购物车按当前会话和数据变更判断有效性，提交令牌采用短期防重复机制。成功后清空购物车并保留本次确认结果供重试查询；失败保留购物车并提示原因。

确认状态必须由服务端控制：同一令牌的检查、业务事务和消费标记应在受锁保护的处理区内衔接，成功后重试返回原结果；失败不得冒充成功。若采用多进程部署或要求跨重启的幂等保证，再增加持久化幂等机制，不默认扩张首版数据模型。

## 6. 待确认后的调整

- 确认 Java 框架与数据库后输出实际迁移文件或建表脚本，本稿不冒充已运行 SQL。
- 注册、还书和购物车已纳入本稿，不再作为待确认功能。
- 如果学校要求审批意见、支付、单双周等内容，再针对确切需求增加字段，不提前预留大量空字段。

## 7. 数据文件与跨电脑迁移（SQLite 建议方案）

- 使用发行目录外部的 `data/campus.db`，通过 Java 的 SQLite JDBC 驱动读写，不要求目标电脑安装 SQLite 服务。
- 数据库文件不放进 JAR 或前端资源目录，不使用开发电脑的 `D:` 盘绝对路径。启动脚本固定工作目录为发行目录，并确认该目录可写。
- 空数据库首次启动时建立表和演示班级、管理员；之后启动不覆盖已有账号和业务记录。后续结构变化采用版本化迁移，不删除数据库重新初始化。
- 若要携带原有数据，先正常停止程序，再复制整个 `data/` 目录；若需要运行中备份，必须使用 SQLite 备份机制，不直接复制正在写入的单个数据库文件。
- 程序重启及移机不迁移内存对话、推荐或购物车，用户重新登录及推荐；已提交请假、借阅和订单必须保留。
- 若最终使用 MySQL，则交付建库/迁移脚本及数据库导出导入步骤，不能靠复制 SQLite 文件迁移。
