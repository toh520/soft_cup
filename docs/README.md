## 使用约定

- 以根目录 `项目要求.txt` 的功能要求为原始依据，新文档不记录其密钥内容。
- “明确要求”来自原始要求及用户后续明确补充；“建议默认”是为了落地补充的实现规则，尚未获得用户确认；“待确认”不能视为已确定需求。
- 管理员预置、学生注册、简单借还书、个人中心身体信息及购物车下单已确认；后端 Java、前端 Vue 已确认，框架、数据库及发行形式仍为建议。
- 需求变化先更新需求规格说明书，再同步数据库和验收清单。
- 编写代码前阅读根目录 [AGENTS.md](../AGENTS.md) 及开发规范，按源码位置、分层、命名和注释约束实现，完成后逐项自检。
- 用户已于 2026-10-15 要求开始开发和测试，当前源码已实现，验证记录见 [开发测试报告](开发测试报告.md)。

## 本次确认与下一步

- 所有项目源码、测试、构建配置及配置模板放在 `code/`，前后端独立、业务模块分层；规范英文命名，关键逻辑有必要中文注释。后续AI按AGENTS指引及开发规范执行。
- 校园知识问答、校园服务助手是两个独立入口与对话窗口；前者采用 RAG 回答知识，后者通过受控工具处理请假、借书、本人课表查询。跨模块请求提供跳转入口，会话及工具分别管理。
- 请假助手追问缺项，自动填写表单并在对话内展示，用户可修改，点击确认提交后才生成待审批申请。姓名、学号直接使用登录信息。
- 管理员账号预置；学生自行注册，只填姓名、学号、密码，以学号登录。
- 借书与还书直接完成，保持简单，不增加审批或复杂图书馆规则。
- 身体数据在个人中心维护；AI 推荐前检查完整性，不齐全提醒补全。
- 按一顿饭推荐，沿用每次三个套餐；选择一个加入购物车，在购物车提交后记录简单订单。
- 购物车建议一次保留一个套餐，可移除或替换，临时保存、不增加数据库表；多套餐及数量编辑未列入当前简单设计。
- 另一台电脑下载源码后须能按环境依赖清单配置并手动运行；开发时持续记录实际验证的依赖版本、安装命令、配置、数据库初始化、前后端运行命令及工作目录。不要求启动脚本、Docker、虚拟环境或附带运行时。
- 两台电脑均为 Windows；知识问答已确定采用向量检索 RAG，管理员按条保存资料时自动向量化，回答必须依据数据库原文，未找到或材料不足时明确提示未查询到。
- 建议 SQLite 保存原文及向量，Java 计算相似度，不增加独立向量服务；embedding 模型及接口尚待选定，与聊天模型分别配置。
- 当前实现采用 Java 21、Spring Boot 3.5.16、Vue 3、Vite、SQLite；环境清单已更新实际命令。真实模型请求返回 401，embedding 服务及门槛仍待有效权限后验证。

其他建议默认仍在正文标出，可继续调整。

新增迁移 `002_plaintext_passwords.sql` 和 `003_demo_materials.sql`，旧数据库升级后一次补充，重启不重复插入、不覆盖已有同学号/同标题资料和已修改密码；课程新增前检查时间冲突。三个学生：`20260001` 张晨（身体信息完整、饮食不限）、`20260002` 林悦（身体信息完整、素食、避开花生）、`20260003` 王宁（身体信息未填）。新演示账号初始密码均为 `123456`。空库总计 1 管理员、3 学生、10 本图书、10 条课程、16 道菜和 12 条校园知识；不预填业务成功记录。

由于目前没有可用 embedding 配置，迁移中的演示知识以明确的 `embedding_model=pending`、`embedding=[]` 保存原文。这个空数组不是有效向量，管理页标“待向量化”，问答返回待建索引的明确提示，不执行检索或用伪造向量回答。用户可查看、编辑或删除这些资料；配置有效 embedding 后“重建全部向量”会按原有全量原子规则转为可检索资料。正常管理员新增/编辑仍自动向量化成功才保存，失败保留旧版本。

本节覆盖此前“只存密码哈希”和“初始化知识库为空”的旧阶段说明。模型密钥仍仅在私有配置保存，真实 AI 服务的 401 和 embedding 配置待定不受此修改影响。


## 2026-10-16 真实模型配置修复与验收

已确认原始需求的 API Key 含点号。此前探测使用了只匹配 `sk-` 后字母数字的截断规则，误将不完整密钥发送给服务并得到 401；该 401 不能代表完整凭据无效。现按完整凭据验证，`qwen3.8-flash` 聊天与同地址 `text-embedding-v4` 均可用，实际向量维度 1024。

完整配置仅写入 Git 忽略的 `code/backend/config/application-local.properties`，由既有 Spring 配置导入机制加载，不在源码、模板、前端或本文保存真实 Key。新电脑需单独配置这个私有文件，源码下载不会携带密钥；不能用按字符集截取的片段代替完整凭据。

当前服务地址为需求中已公开的兼容接口；embedding 独立配置使用同一可用服务及模型 `text-embedding-v4`，维度 1024、Top-K=5。以现有十二条资料和十个问题校准：五个正例最高相似度 0.6568～0.7904，三个无关问题 0.2392～0.2511，两个相似但缺事实问题约 0.4950～0.5005。首轮门槛设为 0.454，使相似缺事实候选交给模型判断能否回答；此门槛仅适用于当前模型与演示语料，新增语料需复核。

十二条 pending 演示资料已通过管理员重建接口调用真实 embedding 全部成功，原文与 1024 维向量一致落库。真实问答验证：宿舍限电回答 300W、借阅期限回答 30 天且均有实际来源引用；热水费、奖学金截止日期返回未查询到；烘焙问题无关返回未查询到。以上覆盖此前“服务未配置/知识未向量化”的状态，历史模拟测试仍仅表示模拟结果。

真实膳食测试发现完整候选列表可能超过原 30 秒等待。现将候选按能量接近程度取前十二个，模型只接收候选标识、菜名/类别和后端营养合计，保留完整服务端快照与输出校验；聊天读取超时调整为 60 秒，连接仍最多 10 秒。候选不足三个仍停止调用，不增加假模型或规则推荐兜底。


## 2026-10-16 食堂整合与手动点餐（当前实现）

食堂现在同时展示显眼的 AI 推荐入口、今日菜单和本餐购物车。学生导航保留助手、知识问答、食堂、个人中心四项，旧 `/cart` 跳转 `/nutrition`；购物车 API 仍由 order 模块管理，未把订单逻辑挪进页面或 nutrition Repository。

`GET /api/nutrition/dishes` 为学生提供当前供应菜品；`PUT /api/cart/items/{dishId}` 接收 `{quantity:整数0～20}`，0 移除、1～20 设置绝对份数。身份从登录会话读取，菜名、供应和营养只用服务端数据，拒绝伪造营养/归属字段。手动点餐无需身体数据和模型服务；AI 推荐保持原身体检查与合法组合筛选。

购物车仍为登录会话内存状态，使用 source 区分 manual/ai、每道菜的服务端快照和 quantity。点击生成只展示推荐；选用 AI 方案直接覆盖手动餐（每菜一份），使旧提交令牌失效。在 AI 餐中继续改数量或加减菜会转为手动搭配。等待 AI 时后端不持有会话购物车锁，手动点选可正常完成；模型返回不改用户购物车。

数据库迁移新增 `004_order_item_quantity.sql`：`order_items.quantity INTEGER NOT NULL DEFAULT 1 CHECK(quantity BETWEEN 1 AND 20)`。原订单每份营养快照保留，旧明细数量补为 1。新手动订单可含任意非空供应菜品组合；营养合计乘数量，历史页面展示菜名 ×份数。仍不涉及支付、配送、价格或业务审批扩展。

界面使用项目 frontend-design 技能重新设计：墨蓝与雾白为主、薄荷/麦黄用于食堂信息，移除导航编号及装饰性全大写标题；统一侧栏、登录、聊天、表单、管理表格，食堂以餐盘 SVG 插画作为视觉重心。餐盘和图标均为项目本地组件，不引入图片服务或新增前端依赖。详细布局见 [界面布局设计](界面布局设计.md)。

源码新增 nutrition 下的 DishMenu、DishArtwork、CanteenCart、useCanteen，shared 下 AppIcon，样式分为 main.css 和 canteen.css；原独立 CartPage 移除，cart API 保留复用。手动失败保留购物车，数量变更和选用方案重新生成确认，订单仍事务写入并幂等。
