## 1. 项目目标与范围

构建用于课程设计演示的智慧校园系统，实现校园服务智能体助手、智能营养食堂、校内知识智能问答、个人信息及管理员管理五个模块。

重点是功能逻辑完整、数据真实落库、智能调用可验证、流程可演示。数据库保持简单，不对接真实教务、图书馆、支付或食堂平台。

### 1.1 明确要求

- 助手通过对话理解需求，可生成请假草稿、查询图书并生成借书请求、查询当前学生课表。
- 请假必须由管理员审批；图书、课表、菜品、校园知识由管理员管理。
- 管理员账号预置；学生使用姓名、学号、密码自行注册，以学号登录。
- 借书确认后立即成功，无借阅审批；支持简单还书并恢复库存。
- 身体数据属于个人信息模块；使用 AI 推荐前检查完整性，不齐全则提醒并引导前往个人中心补全。
- 营养食堂按一顿饭推荐，沿用原始要求每次提供三个合理套餐；学生选择一个套餐加入购物车，在购物车提交订单，仅记录简单订单信息。
- 知识问答只根据已检索到的校园知识回答，未命中时明确告知未查询到。
- 校园知识问答与校园服务助手是两个独立功能、两个独立对话窗口；问答负责查询资料，助手负责办理业务。
- 个人信息展示个人情况、课表、借书记录和订单记录。
- 智能能力通过调用 LLM 实现；接口密钥放在独立配置中，不暴露给前端。

### 1.2 建议默认及范围排除

| 项目 | 当前规则及确认状态 |
| --- | --- |
| 应用形式 | 按已选 Vue 设计浏览器 Web 系统，学生端与管理端共享 Java 后端 |
| 账号 | 已确认：管理员预置，学生自行注册，学号登录 |
| 班级 | 原始要求仅一个演示班级；建议注册时自动归入该班级 |
| 借阅 | 已确认：确认即借阅成功；支持最简还书，无管理员审批 |
| 食堂 | 已确认：一顿饭推荐、套餐加入购物车后提交订单；建议不涉及价格、支付、配送、取餐码、销量统计 |
| 购物车 | 建议最简设计：一次保留一个选中的套餐，可移除或替换，不做数量编辑、跨设备同步 |
| 课表 | 固定每周循环，不处理单双周、学期、节假日与调课 |
| 知识检索 | 已确认采用向量检索 RAG，管理员按条维护，保存时自动向量化；建议 SQLite 存向量、Java 计算相似度 |
| 对话历史 | 当前会话临时保留，不建立历史消息表 |
| 系统时间 | `Asia/Shanghai`，统一由后端解释“今天”等日期表达 |

暂不实现：角色权限配置器、审批工作流引擎、消息推送、文件上传、真实业务平台对接、医疗诊断、长期营养干预、大屏统计。

## 2. 用户角色和权限

| 角色 | 权限 |
| --- | --- |
| 学生 | 注册及学号登录、使用助手、提交本人请假、查询及借还图书、查看本人课表、生成膳食套餐、购物车下单、知识问答、修改本人基础及身体信息、查看本人记录 |
| 管理员 | 管理学生账号和班级归属、维护图书和课表、维护菜品和知识、审批请假、查看业务记录 |

注册与登录是身份入口。所有后端业务写入和个人记录查询都必须验证登录身份；学生不得通过修改请求中的用户 ID 操作他人数据。管理员不需要绕过学生身份替学生借书或下单。注册接口只能创建学生，不能提交自选角色创建管理员。

## 3. 页面与导航

### 3.1 学生端

1. 登录与注册页：学生学号登录、管理员账号登录；注册只填写姓名、学号、密码。
2. 校园服务助手：独立对话窗口，处理请假、图书查询与借阅、本人课表查询，展示业务结果卡片及确认操作；简单还书仍提供个人中心入口。
3. 营养食堂：身体信息完整性提示、前往个人中心入口、推荐按钮、三个套餐及“加入购物车”操作。
4. 购物车：选中的套餐、菜品及营养摘要、移除操作、提交订单和结果反馈。
5. 校园知识问答：独立对话窗口，使用 RAG 回答资料库相关问题，展示来源标题及依据原文，不提供业务提交操作。
6. 个人中心：个人信息编辑、身体与饮食信息、课表、请假记录、借书记录（含归还）、订单记录。

个人中心增加请假记录属于建议补充，用于查看审批进度。无需单独设计营销首页。

两个对话窗口提供独立导航入口、消息列表和会话上下文。切换页面不把另一个窗口的聊天内容或业务草稿自动传入；账号和登录态共用。营养食堂、购物车保留自己的页面与下单流程。

### 3.2 管理端

导航包含学生管理、请假审批、图书管理、借阅记录、课表管理、菜品管理、知识管理、订单记录。列表至少有空状态、加载状态、失败状态和操作反馈；业务状态和库存用直观字段展示。

## 4. 功能需求

### 4.1 登录与个人信息（AUTH / PROFILE）

- `AUTH-01`：账号和密码正确后进入所属角色页面；错误时给出统一登录失败提示。
- `AUTH-02`：支持退出登录，退出后不能继续请求受保护接口。
- `AUTH-03`：开放学生注册，仅填写姓名、学号、密码；成功后提示使用学号登录，不增加邮箱、手机、验证码或注册审批。
- `AUTH-04`：学号不可重复，空姓名、空学号、空密码不能注册；建议学号按字符串保存，保留前导零，长度 1～32，只允许字母或数字，不假定学校固定学号位数；姓名建议 1～50 字，密码建议 6～64 字符。
- `AUTH-05`：后端固定新用户角色为学生，建议自动归入唯一演示班级；身体字段初始为空，注册不要求填写。
- `AUTH-06`：重复学号提示“该学号已注册”；按 2026-10-16 用户新要求，注册成功后数据库保存原密码；注册接口不得覆盖已有用户或接受管理员角色参数。
- `PROFILE-01`：展示姓名、学号、班级和身体信息；学号、角色和班级归属不能由学生自行修改。
- `PROFILE-02`：学生可修改姓名、身体信息与饮食偏好；账号字段保存学生学号，不另设重复学号字段。
- `PROFILE-03`：课表、借书记录、订单记录和请假记录均来自数据库，不使用固定前端假数据。
- `PROFILE-04`：身体信息在个人中心维护，可为空，不影响校园助手及知识问答；点击 AI 推荐时前后端都检查必填项。不齐全时列出缺失字段、提醒前往个人中心并提供跳转入口，不发起模型调用。
- `PROFILE-05`：补全保存后可返回营养食堂重新推荐；食堂不再单独维护第二份身体数据，也不要求在聊天中补全身体信息。

### 4.2 校园服务智能体助手（ASSIST）

#### 4.2.1 意图识别和工具调用

- `ASSIST-01`：LLM 识别请假、图书查询与借阅、本人课表查询等受支持的业务意图，并提取业务参数；支持同义表达和多轮补全。不扩展为通用闲聊或校园知识问答。
- `ASSIST-02`：参数不足时只追问缺失内容；语义不确定时向学生确认，不自行决定日期、书籍或请假理由。
- `ASSIST-03`：LLM 使用受控工具接口访问数据，不直接运行任意 SQL 或任意代码；后端校验工具名称、参数类型、身份和权限。
- `ASSIST-04`：助手中的请假提交、借书需学生显式点击确认，聊天文本本身不触发业务写入。还书由个人中心确认，下单由购物车提交，均遵守对应确认规则。
- `ASSIST-05`：本阶段建议每条消息处理一个主要意图；出现多个请求时询问先处理哪一项，避免一次消息发生多个写入。
- `ASSIST-06`：用户切换意图或改变关键条件时更新草稿，旧确认卡片作废；确认前的草稿不建立数据库业务记录。
- `ASSIST-07`：模型失败时显示可重试错误，不编造课程、库存、审批结果；已确认操作的最终状态以数据库为准。
- `ASSIST-08`：助手仅调用受控业务服务，不接入校园知识 RAG 检索流程。遇到“宿舍限电多少瓦”“借阅期限是多少”等规定问答，简短提示前往校园知识问答并提供入口，不自行回答政策内容；遇到点餐需求引导到营养食堂。
- `ASSIST-09`：请假信息收集完整后，由结构化数据在对话内渲染请假表单卡片，展示姓名、学号、起止时间、理由及“修改内容”“确认提交”按钮。姓名及学号来自登录信息；确认后才创建待审批申请，不能只用一段模型文字代替可操作表单。

#### 4.2.2 请假（LEAVE）

基本字段：申请人、开始时间、结束时间、理由、当前状态。申请人由登录身份确定，不需要学生重复输入。

流程：

1. 学生表达请假需求。
2. 助手提取开始时间、结束时间、理由；缺失则逐项追问。
3. 输出完整草稿，展示申请人、具体日期时间、理由。
4. 学生可补充修改，点击“提交申请”后后端校验并保存为待审批。
5. 管理员选择通过或拒绝；学生在个人中心查看结果。

- `LEAVE-01`：开始时间必须早于结束时间，理由不能为空。
- `LEAVE-02`：出现“明天”“下周一”等表达时转为明确日期；仅有日期、没有时间时追问，不默认全天。
- `LEAVE-03`：建议只接受开始时间不早于当前时间的申请，是否允许补假待确认。
- `LEAVE-04`：状态仅有待审批、已通过、已拒绝；管理员只可处理待审批记录。
- `LEAVE-05`：建议提交后不允许修改或撤销，审批结果不可再次修改；首版不增加审批意见字段。
- `LEAVE-06`：防止重复点击导致重复申请，同一确认令牌只可成功提交一次。

#### 4.2.3 图书查询与借阅（BOOK）

图书基本字段：书名、作者、内容简介、可借数量。

流程：

1. 学生提供书名或相关描述。
2. 后端检索现有图书，助手展示真实匹配结果和库存。
3. 多条匹配时让学生选定具体图书；未匹配时提示未找到。
4. 有可借数量时生成借阅确认卡片，每次借一本。
5. 点击“确认借书”后在一个事务内复查库存、扣减数量、保存借阅记录。

- `BOOK-01`：库存为零时提示暂无可借图书，不生成可提交的确认操作。
- `BOOK-02`：库存并发变化导致无法借阅时返回明确失败，不产生借阅记录。
- `BOOK-03`：建议同一学生不能同时借阅同一图书两次，归还后可再次借阅。
- `BOOK-04`：在个人借书记录提供“归还”操作，点击确认后直接标为已归还并恢复一个可借数量，不经过管理员审批；已归还记录保留用于查看历史。
- `BOOK-05`：重复确认借阅或重复归还不能重复扣减或增加库存。
- `BOOK-06`：管理员维护可借数量，已有借阅记录的图书不允许直接删除，避免历史记录失效。

借还书按简单数据维护实现，不增加借阅审批、归还验收、预约、期限或罚款。图书目录由管理员增删改查，借阅记录由借书创建、还书更新；保留业务记录，不能通过直接删除借阅记录绕过库存更新。

#### 4.2.4 课表查询（SCHEDULE）

基本字段：课程名称、教师、星期、开始时间、结束时间、教室，以及所属班级。

- `SCHEDULE-01`：查询登录学生所属班级课表，无需手动同步或复制个人课表。
- `SCHEDULE-02`：支持今天、明天、指定星期及整周查询；指定日期按星期映射到固定周课表。
- `SCHEDULE-03`：按开始时间升序展示课程名称、教师、时间和教室。
- `SCHEDULE-04`：当天无课时回答无课程；未分配班级时提示联系管理员；已分配班级但整周无记录时提示课表尚未配置。
- `SCHEDULE-05`：管理员更新后，学生下一次查询读取最新数据。

### 4.3 智能营养食堂（NUTRITION / CART / ORDER）

#### 4.3.1 身体与饮食数据

以下数据统一在个人中心录入和修改；注册时不必填写。AI 推荐只读取当前登录学生的个人信息，先检查必填字段，缺失时提醒补全并停止推荐。

| 数据项 | 必填 | 用途 |
| --- | --- | --- |
| 年龄（岁） | 是 | 估算基础代谢；首版建议服务成年学生 |
| 生理性别（男 / 女） | 是 | 用于所选能量估算公式，不用于权限或展示分类 |
| 身高（cm） | 是 | 基础代谢估算 |
| 体重（kg） | 是 | 基础代谢估算 |
| 日常活动水平（低 / 中 / 高） | 是 | 估算每日能量需求 |
| 饮食偏好（不限 / 素食） | 否 | 过滤不符合偏好的菜品，默认不限 |
| 需避开的食材 | 否 | 排除录入过敏原或禁忌标签的菜品，默认空列表 |

建议不收集疾病、病史、BMI 存储值、身份证、手机号等无关字段。BMI 如需展示可由身高体重计算，不入库。

建议输入范围：年龄 18～80 岁、身高 100～250 cm、体重 25～250 kg；超出范围提示首版暂不支持，不声称医学合理性。其他年龄段不使用成年公式直接推断。

#### 4.3.2 菜品数据

| 数据项 | 要求 |
| --- | --- |
| 名称 | 必填 |
| 类别 | 主食 / 蛋白类 / 蔬菜 / 汤；用于组合一顿饭 |
| 每份重量（g） | 必填，所有营养数据均按这一标准份计算 |
| 每份能量（kcal） | 必填，正数 |
| 每份蛋白质、脂肪、碳水化合物（g） | 必填，非负数 |
| 食材与过敏原标签 | 简单字符串列表；管理员尽可能标全主要食材、酱料及常见过敏原 |
| 是否素食 | 必填布尔值 |
| 是否供应 | 必填布尔值，替代复杂库存和供应时段管理 |

不要求菜品图片、价格、销量、评分、营养数据库对接。营养数据由管理员人工录入，允许合理估算；不得标成专业医学检测结果。

#### 4.3.3 推荐逻辑

- `NUTRITION-01`：点击推荐先检查个人中心身体信息，缺失时提示具体缺项并引导补全，不调用 LLM；完整且有效时按一顿饭推荐；未填写本次要求时由一份主食、一份蛋白类、一份蔬菜组成，填写时按本次合法约束组合（见2026-11-10补充）。
- `NUTRITION-02`：后端先筛选供应中的菜品、素食条件和禁忌标签，再构造候选组合；素食用户需有豆制品等素食蛋白菜品。
- `NUTRITION-03`：建议使用 Mifflin-St Jeor 成年人公式估算基础代谢：男性 `10×体重 + 6.25×身高 - 5×年龄 + 5`，女性末项为 `-161`。
- `NUTRITION-04`：低 / 中 / 高活动系数建议为 `1.2 / 1.55 / 1.725`；单餐目标能量建议为每日估算需求的 `35%`。
- `NUTRITION-05`：候选组合总能量建议在单餐目标的 `±25%` 内，默认具备主食、蛋白及蔬菜的结构，本次要求可调整菜品组成。三大营养素用于展示和辅助排序，首版不宣称符合个体医疗营养要求。
- `NUTRITION-06`：LLM 从后端提供的合法候选中选择三个不同方案并解释推荐理由；不能发明菜品、菜品 ID、营养数值或忽视过滤条件。
- `NUTRITION-07`：后端校验模型返回结构、菜品 ID、方案唯一性和营养总量；能量和三大营养素合计均由后端计算。
- `NUTRITION-08`：不足三个合法组合时不复制方案凑数，提示暂不足三个方案及需要补充的菜品类别；不自动放宽食材禁忌。
- `NUTRITION-09`：模型调用失败或返回无效结构时提示失败并支持重试，不冒充已完成智能推荐。首版不要求纯规则兜底。
- `NUTRITION-10`：界面简短说明“能量与营养为估算值，非医疗建议；严重过敏请向食堂核实”。标签过滤不能保证实际制作过程无交叉接触。

以上公式、系数和单餐比例为可解释的课设默认规则，不是学校明确要求，需确认后采用。

#### 4.3.4 购物车

流程：个人中心补全身体信息 → 点击 AI 推荐 → 展示三个套餐 → 选择一个加入购物车 → 进入购物车核对 → 提交订单 → 查看订单记录。

- `CART-01`：推荐卡片展示菜品、标准份量、总能量、三大营养素和简短理由，操作按钮为“加入购物车”；加入购物车不创建订单。
- `CART-02`：建议首版购物车一次保留一个套餐，每道菜一份。重复加入同一套餐提示已加入；加入不同套餐时询问是否替换，不默认累加多个套餐或增加份数。
- `CART-03`：购物车展示已选套餐及菜品、营养摘要，可移除；空购物车提示先选择套餐，不能提交订单。
- `CART-04`：推荐及购物车属于登录学生，后端校验来源；前端传入一个任意套餐名称不能成为有效购物车。
- `CART-05`：建议用服务端临时状态保存购物车，不新增数据库表；当前登录会话内刷新页面可恢复，退出登录或服务重启后清空，不要求跨会话、跨设备同步。
- `CART-06`：身体信息、禁忌或菜品关键数据发生变更后，旧套餐标为失效并提示重新推荐；不把变更后的营养值悄悄替换为已选套餐值。

上述单套餐容量和临时保存方式是保持简单的实现建议；如果后续要求同时购买多个套餐，再增加数量及相应明细设计。每次仍推荐三个套餐，原始要求的推荐数量未被本次补充改变。

#### 4.3.5 提交订单和记录

- `ORDER-01`：用户在购物车点击“提交订单”才创建订单，后端读取并复查本人的有效购物车及菜品供应状态。
- `ORDER-02`：提交成功保存订单 ID、学生、三道菜品快照和下单时间；个人中心和管理员可查看简单订单记录。
- `ORDER-03`：订单无价格、支付、配送、出餐或取消流程；不单独设置套餐表，不保存无用途的推荐过程记录。
- `ORDER-04`：提交使用绑定用户及当前购物车内容的确认令牌或等价幂等机制，同一次提交重试只创建一张订单。
- `ORDER-05`：成功后清空购物车并展示订单 ID；失败保留购物车及错误提示，已失效套餐必须重新推荐后再提交。
- `ORDER-06`：服务端产生下单快照，不接受前端伪造菜名或营养值；历史订单不因菜品改名或营养修改而改变。
- `ORDER-07`：菜品下架、购物车不存在、推荐状态失效或提交令牌过期时不创建订单。推荐及购物车按当前会话和数据变更判断有效性；提交令牌按独立短期确认机制处理。

### 4.4 校内知识智能问答（QA）

知识按一条条条目存储，字段为标题、类别、正文。类别建议为学校规章制度、专业课程信息、校园活动、其他。

资料流程：管理员新增或修改标题、类别、正文 → 后端调用 embedding 模型生成向量 → 原文与向量一致保存 → 后续问答可检索。

问答流程：用户问题向量化 → Java 对数据库中兼容向量计算相似度 → 按相关性筛选候选 → LLM 根据原文判断能否回答并整理答案 → 展示回答、来源标题及依据原文。

- `QA-01`：采用向量检索 RAG，实现“宿舍限电多少瓦”与“宿舍对于电器的最大功率为300w”等不同表达的语义匹配，不要求问题与原文共享完全一致的词语。
- `QA-02`：管理员每次录入一条有标题的知识短文；新增或修改标题、正文时自动调用 embedding，原文与对应向量必须一致。失败不提示保存成功；编辑失败保留原版本及原向量。删除时同时移除原文与向量。
- `QA-03`：资料与问题使用同一 embedding 模型及相容配置。建议按余弦相似度取最多五条超过相关性门槛的候选，门槛通过演示问答调试，不把排名第一直接视为有效命中；模型和阈值配置见 RAG 设计。
- `QA-04`：语义相关不等于能够回答；模型必须判断原文是否包含所问事实，支持不足时仍返回未查询到。向量不替代知识原文，答案中的具体数字、日期和规定只能来自原文。
- `QA-05`：有依据时回答并列出实际使用的来源标题及依据原文；模型输出的来源 ID 必须属于候选集合。引用原文由后端核对并从数据库提供，不接受模型伪造的引用；来源或原文不合法时本次回答校验失败。
- `QA-06`：没有命中或材料不足时统一回答：“暂未查询到相应的知识点。”
- `QA-07`：校园规则、活动时间、课程安排不得由模型常识补全；知识内容与问题中包含的“忽略规则”等文本不能改变系统工具权限。
- `QA-08`：模型超时或服务异常与无知识命中区分提示，不能把接口失败误报为知识库没有内容。
- `QA-09`：管理员新增、编辑、删除知识后，下次问答读取最新数据库内容。
- `QA-10`：不得在检索无结果时调用模型凭常识生成校园答案；存在相关条目但缺少用户询问的关键事实（如具体截止日期）时，也必须告知暂未查询到，不补写日期、数字或政策。
- `QA-11`：本窗口只提供知识问答，不调用请假、借阅、归还或下单写入工具。遇到“帮我请假”“帮我借书”“查我今天的课”等业务请求，提示前往校园服务助手并提供入口，不在问答窗口继续收集业务参数或生成确认卡片。查学校课程介绍属于知识问答，查本人实际课表属于业务查询。
- `QA-12`：知识问答与服务助手的后端路由、提示词及可用工具分别设置；问答端不能仅凭模型输出的工具名执行业务接口。两者会话按用户及模块隔离，可共用聊天模型客户端和登录鉴权。

本模块的目标是基于数据库内容回答。检索方式决定能否找到内容，向量化不是避免编造的充分条件。提示词、来源 ID 和引用校验能约束回答，但单凭这些不能证明生成文字中的每个事实都正确；验收需核对回答与原文是否一致。如需要严格只展示数据库已有文字，可采用抽取式结果直接展示原文，AI 摘要作为可选展示方式。

向量化与语义检索已列为首版必做。首版建议每条短文作为一个检索单元，无需独立向量数据库；具体实现、保存一致性及验收示例见 [RAG知识问答设计](RAG知识问答设计.md)。embedding 模型及其地址、权限和费用尚待确定，不能假定现有聊天接口已提供 embedding 能力。

## 5. 全局业务与安全规则

1. 所有业务数据以数据库为准，LLM 仅负责理解、选择和表述。
2. 写入接口校验身份、字段范围及业务状态，不能仅依赖模型提示词或前端校验。
3. 确认操作使用短期、绑定用户和业务内容的确认令牌或等价机制，限制重复请求；具体存储方式在开发时确定，不要求为草稿建立数据库表。
4. 借阅、归还、订单主明细写入和审批状态变更使用事务；多次审批只有第一次符合状态条件的更新可成功。
5. 删除受关联约束保护；不得级联删除请假、借阅、订单等业务历史。
6. 按 2026-10-16 用户新要求保存原密码，管理员可查看学生密码；模型调用由后端发起，前端、日志、错误响应不得包含密钥。
7. 仅将完成任务所需的数据传给模型；不发送密码哈希、密钥、完整账号列表或其他学生记录。
8. 基础日志记录接口结果与异常，不默认记录完整身体数据、请假理由和对话原文。
9. 使用参数化数据库访问；对知识正文和模型输出进行安全文本渲染，不直接插入任意 HTML。
10. 本地单机演示是最低交付目标；公网部署、长期审计、生产级高可用不在当前范围。

## 2026-10-16 真实模型配置修复与验收

已确认原始需求的 API Key 含点号。此前探测使用了只匹配 `sk-` 后字母数字的截断规则，误将不完整密钥发送给服务并得到 401；该 401 不能代表完整凭据无效。现按完整凭据验证，`qwen3.8-flash` 聊天与同地址 `text-embedding-v4` 均可用，实际向量维度 1024。

完整配置仅写入 Git 忽略的 `code/backend/config/application-local.properties`，由既有 Spring 配置导入机制加载，不在源码、模板、前端或本文保存真实 Key。新电脑需单独配置这个私有文件，源码下载不会携带密钥；不能用按字符集截取的片段代替完整凭据。

当前服务地址为需求中已公开的兼容接口；embedding 独立配置使用同一可用服务及模型 `text-embedding-v4`，维度 1024、Top-K=5。以现有十二条资料和十个问题校准：五个正例最高相似度 0.6568～0.7904，三个无关问题 0.2392～0.2511，两个相似但缺事实问题约 0.4950～0.5005。首轮门槛设为 0.454，使相似缺事实候选交给模型判断能否回答；此门槛仅适用于当前模型与演示语料，新增语料需复核。

十二条 pending 演示资料已通过管理员重建接口调用真实 embedding 全部成功，原文与 1024 维向量一致落库。真实问答验证：宿舍限电回答 300W、借阅期限回答 30 天且均有实际来源引用；热水费、奖学金截止日期返回未查询到；烘焙问题无关返回未查询到。以上覆盖此前“服务未配置/知识未向量化”的状态，历史模拟测试仍仅表示模拟结果。

真实膳食测试发现完整候选列表可能超过原 30 秒等待。现将候选按能量接近程度取前十二个，模型只接收候选标识、菜名/类别和后端营养合计，保留完整服务端快照与输出校验；聊天读取超时调整为 60 秒，连接仍最多 10 秒。候选不足三个仍停止调用，不增加假模型或规则推荐兜底。

## 2026-11-10 标签页独立登录与本餐要求（当前实现）

用户明确要求同一浏览器每个标签页独立登录不同账号，且 AI 推荐可以附带一句本次用餐要求。本节覆盖此前共享 Cookie 与固定三菜组合的约定。

- 登录返回独立会话令牌，前端只存当前标签页的 sessionStorage，以 Authorization: Bearer 请求身份。刷新保留本页登录；新标签页默认未登录，复制/带 opener 的标签页检测继承存储后清除凭据。退出、过期只影响对应会话，管理员和学生可在同一浏览器同时操作。
- 后端不再接受 CAMPUS_SESSION Cookie；旧版页面升级后需刷新并重新登录。助手和知识问答在单个标签页内共用当前账号，但仍各有独立对话。切换账号时迟到的旧请求不能恢复旧消息或退出新账号。
- 食堂新增“本次用餐要求（选填）”，最多300字符，只用于这次推荐，不修改个人资料。空白按原规则一主食、一蛋白类菜、一蔬菜推荐。
- 非空要求由模型结合已过滤的真实菜单解析，后端校验数量、合法ID、必选/排除菜品和荤素，构造合法候选后再由模型选三个不同方案。当前支持0～1份主食、0～4道配菜、0～1份汤，合计至少一道。荤素以 isVegetarian 标记判断；汤和主食不占配菜数，豆腐不能因 protein 分类而算荤菜。
- 例：“有荤有素，2菜一汤，主食是米饭”：每个方案必须含米饭、两道配菜（一荤一素）和一道汤，共四项。不得用杂粮饭代替明确指定的米饭。
- 身体资料、档案素食/忌口、供应状态及单餐目标能量±25%仍生效。要求冲突、指定菜品无供应、条件无法确认或合法组合不足三个时明确失败，不默默放宽，不编造菜品。模型超时/无效结构保持错误反馈，重试保留输入。
- 菜品分类增加 soup，学生可按“汤”筛选，管理员可以新增/编辑汤类。新增三种演示汤，升级不覆盖已有菜品。推荐生成不改购物车，选用才整体替换，四项及其他合法数量套餐均可下单并保留历史快照。
