# 校内知识问答 RAG 设计

日期：2026-10-15  
状态：向量检索 RAG 已确认；以下为基于 Java、SQLite 的简化实现设计，尚未编码。

模块边界：本设计仅用于独立的“校园知识问答”窗口。其会话与“校园服务助手”分开，不提供请假、借书等业务工具；用户提出业务办理或本人课表查询时提供助手入口。服务助手通过业务接口办事，不调用此 RAG 流程。

## 1. 资料组织

管理员按条新增、编辑和删除资料，每条包括标题、类别、正文。例如：

- 标题：宿舍用电规范；正文：宿舍对于电器的最大功率为300W。其他说明……
- 标题：宿舍生活指南；正文：宿舍生活的有关说明……

上述内容仅为验收样例，不代表真实学校政策。首版每条短文作为一个检索单元，向量化输入为“标题 + 正文”。限制单条长度以适应所选 embedding 和聊天模型的输入上限；超长时明确要求管理员拆成多条，不静默截断。若后续要求上传长文件，再设计自动分块，本版不做附件上传。

## 2. 保存和向量维护

1. 后端校验标题、正文和长度。
2. 调用独立配置的 embedding 模型，将标题和正文转换为数值向量。
3. 检查维度、有限数值、非零范数和模型标识，在短事务中保存原文、向量及模型标识。
4. 全部成功才反馈保存成功，后续问题使用新数据。

原文与向量保存在同一条数据库记录中，不新增独立向量服务和同步队列。远程模型调用在写入事务外执行，避免长时间锁数据库。

- 新增失败：不留下无法检索的半条记录，提示错误并允许重试。
- 编辑失败：旧原文和旧向量一并保留；不能新原文匹配旧向量。
- 并发编辑：写入前检测生成向量所依据的版本是否已被其他请求修改；发生冲突提示刷新重试，禁止覆盖后来的变更。
- 删除：同一行原文、向量一起删除；不保留孤立向量。若已删除，尚未完成的编辑请求不能重新创建它。
- 首版不缓存独立持久化索引；后续增加缓存时，必须处理删除及更新失效。

## 3. 提问与回答

```text
问题：“宿舍限电多少瓦？”
  -> 同一 embedding 模型生成问题向量
  -> Java 计算问题与知识向量的余弦相似度
  -> 筛选超过相关性门槛的候选，最多取 Top-K 条
  -> 将候选 ID、标题和原文交给聊天 LLM
  -> 原文包含答案：回答“宿舍电器最大功率为300W”，附来源和原文
  -> 未找到或原文无所问事实：“暂未查询到相应的知识点。”
```

Top-K 建议初值为 5。相似度门槛随 embedding 模型和资料内容变化，用正例、同义问法、近似但无答案及无关问题测试后确定，不预设某个分数能保证正确。

模型返回结构至少包含是否可回答、回答文本、来源条目 ID 和依据原文。后端验证来源属于实际候选，引用确实存在于对应数据库原文；不合规输出作为回答生成失败，不展示为有效答案。来源和原文真实性不等于回答每句话都正确，仍需按验收样例核对语义支持。

关键规则：

- 向量只用于找资料；事实答案取自原文，不能从向量本身读取“300W”。
- 相似度最高也可能无关，不能无条件返回第一条。
- 命中“宿舍生活指南”却没有用电功率时，不推断或猜测瓦数。
- 无有效候选时，后端直接返回未查询到，不请求模型自行补答案。
- 问题向量化失败、模型超时、维度不兼容、向量重建未完成等属于服务或配置异常，单独提示，不冒充未找到知识。
- 知识中的指令文本不具备系统权限；生成回答只允许使用提供的原文依据。

## 4. 模型和配置

聊天模型负责理解依据、生成自然语言；embedding 模型负责生成可比较的向量，二者用途不同。已提供的聊天接口并未验证 embedding 能力，后续需要选定并验证可用服务。

建议独立配置项：

```properties
embedding.base-url=
embedding.model=
embedding.api-key=${EMBEDDING_API_KEY:}
embedding.timeout-seconds=30
rag.top-k=5
# 根据选定模型和验收数据确定后填写，不给出未经验证的固定门槛
rag.min-similarity=
```

向量维度从模型能力及实际返回值校验；资料与问题必须使用相容的模型、维度和处理参数。若服务对资料和查询要求不同的 task 类型或前缀，分别按服务文档实现。

更换 embedding 模型、维度或向量化输入规则时，需要重建全部知识向量。建议全库重建成功后再统一启用新配置；未就绪时暂停问答并明确提示，不混用不同向量空间。重建失败保留原始资料及可恢复的旧版本。

embedding 服务可能额外产生调用费用，资料保存和用户提问均涉及调用；不把未验证服务写为已可用，不在本阶段使用真实凭据测试。

## 5. SQLite 与移机

建议 `knowledge_entries` 中保存原文、JSON 向量和模型标识，由 Java 扫描兼容向量计算相似度。对课设少量条目即可运行；数据规模扩大后再评估专用索引，不声称扫描方案能满足大规模性能。

停服后复制数据库文件可同时携带原文和向量；目标 Windows 电脑使用兼容配置和有效密钥即可继续检索，不必每次启动重新向量化。新增资料和新问题的向量化仍需可用 embedding 服务，回答生成仍需可用聊天模型服务。

## 6. 验收重点

- 录入“宿舍电器最大功率为300W”，问“宿舍限电多少瓦”可匹配并引用原文。
- 录入“图书借阅期限为30天”，问“书能借多久”可匹配并回答30天。
- 将300W修改为500W，保存成功后的新问题只引用500W；删除后不再返回该知识。
- 只录入宿舍生活说明但不含功率规定时，不猜瓦数。
- 知识库为空、无关问题、相似但缺答案时返回未查询到。
- 模拟向量化超时、错误维度、并发编辑、删除与编辑冲突，验证数据一致性与明确错误反馈。
